# 雀魂「比赛场」后台直连登分 · 调研与接入方案

> 目标：不靠人工逐个录分，直接从雀魂「比赛场」拉取对局结果，自动写进本系统。
> 本文只做技术调研与方案设计，尚未接入任何账号。

---

## 一、结论先说

**可行，但要另做一个「同步器」**，不能只靠纯浏览器页面：

| 形态 | 可行性 | 说明 |
|---|---|---|
| Windows EXE（Electron 主进程） | ✅ 推荐 | 主进程跑 WebSocket + protobuf，界面里点「从雀魂同步」 |
| 独立小工具（Node 脚本 / 小窗口） | ✅ 可行 | 拉完写成 CSV/JSON，本系统照旧「导入牌谱」 |
| Android APK | ⚠️ 较难 | 需要后台连接、protobuf、登录态；建议仍用 CSV 导入 |
| 纯网页版 | ⚠️ 能做但别扭 | 浏览器可连 WS，但登录 token 暴露在前端，且跨域/证书受限 |

原因：雀魂的对局数据走 **WebSocket + protobuf**，不是普通 HTTP JSON；登录需要账号态（或 oauth token），前端直接做会把凭据暴露在页面里。

---

## 二、协议要点（已从公开的 liqi.json 核对）

雀魂客户端与服务端用 WebSocket 通信，每帧首字节是类型：`0x02` 请求、`0x01` 通知、`0x03` 响应；请求/响应后跟 2 字节序号，正文是 protobuf（结构来自浏览器里的 `liqi.json`）。参见 [mjsoul 协议说明](https://github.com/takayama-lily/mjsoul/blob/master/docs/protocol.md)。

### 与比赛场相关的接口（`lq.Lobby`）

| 消息 | 字段 | 用途 |
|---|---|---|
| `ReqLogin` | `account`, `password`(hash), `client_version_string` | CN 账号密码登录（可能需验证码） |
| `ReqOauth2Auth` | `type=10`, `code`, `uid` | 用浏览器里抓到的 oauth token 登录 |
| `ReqOauth2Check` / `ReqOauth2Login` | `type`, `access_token`, `device`, `client_version` | token 校验与登录 |
| `ReqFetchCustomizedContestByContestId` | `contest_id` | 用比赛场编号换内部 `unique_id` |
| `ReqEnterCustomizedContest` | `unique_id` | 进入比赛场 |
| `ReqFetchCustomizedContestGameRecords` | `unique_id`, `last_index` | **增量拉取已结束的对局** |
| `ResFetchCustomizedContestGameRecords` | `next_index`, `record_list[]` | 返回 `RecordGame` 列表 |
| `ReqFetchCustomizedContestGameLiveList` | `unique_id` | 正在进行的桌 |
| `NotifyCustomContestSystemMsg` | `type`, `uuid`, `game_end` | 对局结束时服务端推送 |
| `ReqStartCustomizedContest` | `unique_id` | 组织者开始比赛（不建议自动化） |

### `RecordGame` 结构（关键）

```
RecordGame
├─ uuid            对局唯一 ID（用来去重）
├─ start_time/end_time
├─ accounts[]      AccountInfo { account_id(雀魂UID), seat, nickname }
└─ result
   └─ players[]    PlayerItem { seat, total_point, part_point_1, part_point_2, grading_score, gold }
```

- `accounts[].account_id` 就是牌谱里的数字 UID，`nickname` 是昵称
- `result.players[].part_point_1 / part_point_2` 是对局点数（一局半庄就取对应字段）
- 比赛场一般「一局 = 一个半庄」，正好对应本系统「每局点数」

这四类数据足够拼出本系统现在支持的雀魂牌谱 CSV（`X位玩家 / X位分数`），所以**现有导入逻辑可以复用**，不需要改数据模型。

## 三、推荐方案：EXE 内「从雀魂同步」+ 复用 CSV 导入

### 数据流

```
雀魂比赛场（unique_id）
   │  WS + protobuf，轮询 fetchCustomizedContestGameRecords(last_index)
   ▼
Electron 主进程同步器
   ├─ 去重（记录已导入的 game uuid）
   ├─ 账号映射（雀魂 account_id ↔ 本系统选手 UID/昵称）
   └─ 生成标准牌谱 CSV
   ▼
渲染层：自动调用现有 csvPlanImport → 预览 → 写入当前轮
```

### 界面设想

赛事 → 阶段 → 编排登分：

```
[📥 导入牌谱 CSV]  [🔄 从雀魂比赛场同步]
```

点「同步」弹窗：

- 比赛场编号（从比赛场链接里取）
- 登录方式：账号密码 / 粘贴 oauth token + uid
- 轮询间隔（默认 15s）、自动写入开关
- 同步日志：已拉取 N 局，新增 M 局，跳过 K 局（已存在 / 桌不匹配）
- 「只同步当前轮」/「自动匹配到对应轮次」

### 为什么用「拉取」而不是「推送」

`fetchCustomizedContestGameRecords` 支持 `last_index` 增量，断线重连后可续拉，比依赖 `NotifyCustomContestSystemMsg` 推送更稳（推送会漏）。两者可以都接：推送只作为「立刻刷新」的触发。

### 登录态怎么来

1. **CN 账号密码**：`ReqLogin{account, password: md5}`，需要处理验证码版本；
2. **oauth token**：在浏览器登录雀魂后，从 WS 帧里抓 `lq.Lobby.oauth2Auth` 的 code 与 uid（[Akane](https://github.com/cozziekuns/Akane) 就是这么做的）；
3. token 落盘要加密/至少限定只存本机，避免写进代码仓库。

### 客户端兼容

- 需要匹配服务端要求的最低客户端版本（`client_version_string`），版本过旧会被拒；
- `liqi.json` 会随版本变化，接入时要把当前版本打包进去，并提供「更新协议文件」入口。

## 四、直接连「比赛场后台」（contest management server）的另一条路

[oscarfzs/majsoulgo](https://github.com/oscarfzs/majsoulgo) 实现了 `dhs.ContestManagerClient`：

- 从 `GetContestManagementServerUrl()` 取后台地址；
- `ReqContestManageOauth2Login{type:10, access_token}` 登录后台；
- 监听 `NotifyContestGameEnd` 拿 `game_uuid`。

这条是**组织者后台**通道，权限要求更高（需要比赛场创建者/管理员身份），协议字段没有公开完整文档，`liqi.json` 里也查不到（是另一套 `dhs` 的 proto）。相比之下，走游戏服 `lq` 的拉取接口更通用、字段更明确，建议先用 `lq` 方案。

## 六、风险与边界

1. **服务条款**：非官方客户端/自动化可能违反雀魂用户协议，账号有被处罚风险；建议只读、低频、用专用账号，并在软件里明确提示「自担风险」。
2. **不伪造对局**：只读取已结束对局，不提供开始/结束比赛、改分能力。
3. **隐私**：同步会拿到参赛者雀魂 UID 与昵称，只有本地保存，不上传。
4. **稳定性**：协议与服务端版本强相关，需要可更新的协议文件与失败重试。
5. **登录限制**：CN 账号可能弹验证码；EN/JP 账号需要第三方 OAuth，不能直接用账号密码。

---

## 七、建议的实施顺序

1. **P0（低风险）**：保持 CSV 导入；把手动导出/粘贴的牌谱做成「一键导入当前轮」。（已完成）
2. **P1**：写一个独立 Node 同步器（本地运行），登录 → 拉取 → 生成 CSV → 本系统导入。先不集成进 EXE，方便验证协议。
3. **P2**：把同步器接进 Electron 主进程，界面加「从雀魂同步」按钮，支持轮询与去重。
4. **P3**：APK 只做「扫码/文件导入」，不同步。

> 注意：P1/P2 需要真实的雀魂账号与一场测试比赛场才能验证，且要自行承担账号风险。
